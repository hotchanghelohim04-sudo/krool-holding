# Architecture multilingue

## Langues natives : FR et EN

- Routage par préfixe : `/fr/...`, `/en/...` (`next-intl`, `localePrefix: "always"`).
  `/` redirige vers la langue préférée du navigateur (FR par défaut) via `src/proxy.ts`.
- Libellés d'interface : `frontend/messages/{fr,en}.json`. **Aucun texte en dur** dans les composants.
- Contenus éditoriaux : `content/` puis base de données (back-office).
- SEO : `alternates.languages` (hreflang) et `canonical` générés dans `src/app/[locale]/layout.tsx`.
- La langue est lue avec `next/root-params` (compatible `cacheComponents`), dans `src/i18n/request.ts`.

Ajouter une clé : l'écrire dans **les deux** fichiers `messages/*.json`, puis
`const t = await getTranslations("Namespace")` (serveur) ou `useTranslations` (client).
Un composant client n'a accès qu'aux namespaces passés à `NextIntlClientProvider` dans le layout.

## Langues automatiques (étape 7)

Liste dans `src/i18n/config.ts` (`machineLocales`). Principe retenu :

```
Navigateur ──► Next.js ──► API Django /api/translate ──► cache (table Translation)
                                         │ manquant
                                         └──► prestataire (DeepL / Google / LibreTranslate)
```

1. Le sélecteur propose FR, EN puis les langues automatiques, avec la mention « traduction automatique ».
2. Une page en langue automatique est rendue depuis sa version **EN** (ou FR), puis les blocs de texte
   sont traduits par l'API Django, qui stocke le résultat (clé du contenu + hash du texte source + langue).
3. Si le texte source change, le hash change et la traduction est régénérée.
4. Les pages juridiques et les référentiels techniques restent en FR/EN, avec un avertissement.
5. Ces pages ne sont **pas indexées** (`noindex`) pour éviter du contenu dupliqué de faible qualité.

Le contrat côté front est défini dans `src/i18n/machine-translation.ts`.
Le prestataire est isolé côté backend : en changer ne touche pas le front.
